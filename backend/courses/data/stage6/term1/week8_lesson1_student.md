# Week 8 - Lesson 1

## Session length
**About half of this week's plan** (you will finish in Lesson 2)

## Today you will learn
- Deliver a 5-minute formal presentation to a panel (you + invited assessor) following the structure: Problem -> Solution -> Live Demo -> Evidence -> Reflection
- Demonstrate a live, working Arduino prototype that responds to input and produces correct output during the presentation
- Explain at least one coding concept used (loop, condition, variable, function) in plain English to a non-technical audience
- Present at least one quantified mathematical outcome — a measurement, calculation, or data point from the project — displayed on a graph or in a data table
- Read a written introduction and conclusion from prepared notes
- Answer a minimum of 2 questions from the panel about the project design, coding decisions, or mathematical elements

## Big idea
ILO 3.4 (summative) — Design, build, test, iterate, and present an original Arduino project integrating coding, English literacy, and Mathematics, supported by a written design brief and a 5-minute formal presentation.

## Let's begin

1. You arrive with projects already built and tested at home or in a pre-session setup window.
2. First 20 min: each pair connects hardware, uploads sketch, and runs a final test. You circulates — any last-minute bugs must be resolved before presentations begin. No new features — bug fixes only.
3. Final 10 min: you review their Design Brief, check they can answer: "What problem does it solve? What coding concept did you use? What is the math connection?" Practise the opening sentence aloud to partner.
4. You confirms presentation order. Remind panel of rubric criteria. Invited assessor receives a copy of the assessment rubric and a 2-minute briefing on the marking criteria.
5. Set room: presenter position at the front, panel seated facing the presenter, audience (other you) in a semicircle. One laptop visible for Serial Monitor output if relevant.
### 2. PRESENTATIONS Formal Demo Day
6. You presents individually for 5 minutes. Partner supports hardware during the live demo portion but does not speak.
7. Presentation structure (enforced): (1) Introduction — read from notes: name, project title, problem addressed. (2) Solution — explain how the project works in plain English. (3) Live Demo — run the project. Narrate what is happening. (4) Evidence — show the mathematical element: graph, data table, or calculation. (5) Reflection — what was hard? What would you improve?
8. Panel questions (2 minutes after each presentation): you ask 1 question; invited assessor asks 1 question. Questions are drawn from: "Why did you choose this component?", "Explain what this line of code does.", "What does your data tell you?", "How did you decide on this design?"
9. Audience: you in the audience completes one Peer Feedback Rubric for the presenter. Forms collected after each presentation.
10. You and assessor score independently on the Demo Day Assessment Rubric during the presentation. Moderate if scores differ by more than 10%.
11. Between presentations: 2-minute transition time. Next presenter sets up hardware.
12. 3. SCORING & CERTIFICATE AWARD
