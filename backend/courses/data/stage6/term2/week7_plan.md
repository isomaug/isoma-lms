# Term 2 · Lesson 7: Your Greatest Build - Capstone Project Design, Build & Documentation

**Duration:** 3 hours (Term-time Saturday) (split across Week 7 Lesson 1 start + Lesson 2 finish)
**Term / Week:** Term 2 · Week 7
**Age Range:** 10–12 years
**Hardware:** Learner-selected from: Arduino Uno, USB cable, TMP36, LDR, buzzer, push button × 2, LED × 4, 220Ω resistors × 4, 10kΩ resistors × 2, breadboard, jumper wires (full component tray per pair)
**Software:** Arduino IDE 2.x
**Bloom's:** L6 Creating
**DDD Phase:** CREATE - Learners produce a complete 7-section Design Brief, build and test a working Arduino prototype that synthesises at least three Term 2 concepts, and give and receive structured peer review using the DDD Part 8.6 rubric criteria
**NCDC:** Uganda NCDC Curriculum P5/P6 - Literacy Strand: Technical design documentation - writing a comprehensive 7-section design brief with structured argument, evidence, and revision history. Numeracy Strand: Applying measurement, statistical analysis, arithmetic sequences, or classification logic as the explicit mathematical element of the project

**Big Idea:** ILO 3.4 (summative) - Design, build, test, iterate, and present an original Arduino project that integrates at least one coding concept, one explicit English literacy connection, and one explicit Mathematics connection, supported by a written design brief (DDD Part 8.5).

**Source plan:** `Stage6_T2_Week7_Capstone_Project.docx`

## Learning Objectives

- Write a complete 7-section Term 2 Design Brief: Problem Statement, Target User, Solution Description, How It Works (step-by-step pseudocode), English/Math Connection, Test Results (minimum 5 runs), Improvements Made (minimum 2 documented changes based on testing)
- Build a working Arduino prototype that incorporates at least THREE of the following Term 2 concepts: modular functions with return values, arrays for data storage, Serial user input, compound threshold logic, rolling mean, rule-based classification
- Demonstrate one explicit and quantified mathematical element in the project - not just mentioned in the brief, but visible and measurable in the prototype's output
- Test the prototype systematically against 5 defined test cases and record results in the Design Brief Test Results section
- Give structured peer review to a partner using the DDD Part 8.6 rubric criteria - written, specific, and evidence-based
- Receive peer review feedback and make at least two documented improvements - recorded in the Improvements Made section of the Design Brief

## Lesson Structure

### 1. HOOK The Engineering Standard
1. Facilitator reads aloud the ILO 3.4 assessment criteria from the DDD (printed on the board): "Functionality (10%): project runs, responds to input, produces correct output. Code quality (10%): variables, loops, functions, comments. Integration (10%): explicit, demonstrable English AND Math connection."
2. Ask: "What is different about Term 2 Week 7 vs Term 1 Week 7?" Collect answers. Key differences: THREE Term 2 concepts required; mathematical element must be quantified and visible; peer review uses the actual DDD rubric criteria.
3. Distribute the Term 2 Design Brief Template. Learners read the mandatory field checklist: "At the top of your brief, tick which THREE Term 2 concepts your project includes. These ticks are your commitment - they become assessment criteria."
4. Pairs have 10 minutes to draft their Problem Statement and complete the mandatory concept checklist. Facilitator approves the Problem Statement before any hardware is touched - if it is too vague, return for revision. Criteria: specific, verifiable, serves an identified user.
5. Distribute and read the Term 2 Peer Review Rubric. Learners know from the start what their partner will be evaluating - this shapes design decisions.
6. 2. SESSION 1 / BUILD PHASE 1 Design Brief + Circuit
7. First 30 min - Design Brief Sections 1–5: Complete Problem Statement, Target User, Solution Description, How It Works (pseudocode - written in English numbered steps BEFORE typing code), English/Math Connection. Facilitator approves How It Works pseudocode: "Can I understand what this does without seeing the code? If not, rewrite."
8. Second 30 min - Circuit Build: select components from tray. Justify each selection on the Design Brief component list: "I need the TMP36 because my project classifies temperature environments." Wire the circuit. Photograph or sketch the wiring diagram in the Design Brief.
9. Facilitator coaching: circulate using ONLY the Socratic coaching card questions. Do not give code. Do not suggest a solution. Ask: "What does this component do? How will you know it works? Where will the math connection appear in your output?"
10. First sketch: write on paper first (pseudocode), then type. No uploading until the pseudocode has been signed off by the facilitator.
11. 3. SESSION 2 / BUILD PHASE 2 Code, Test & Peer Review
12. First 25 min - Complete and test the sketch. Complete the Test Record Sheet: 5 test cases, each with deliberate input conditions. If a test fails, fix and re-test. Document the fix in Design Brief Improvements Made section.
13. At 25 min mark: STOP coding. Switch to peer review. Exchange Design Briefs with adjacent pair. Complete the Term 2 Peer Review Rubric - all 5 criteria, written evidence-based comment for each. Post-it notes may be attached to specific sections of the brief.
14. Final 10 min: receive partner's rubric. Read each comment. Make at least 2 documented improvements based on the feedback. Add these to the Improvements Made section of the Design Brief.
15. Prototype must be in a state where it can be picked up and demonstrated without re-coding next week. Label the hardware with pair names. Save the sketch to USB flash drive.
16. Extension: Add a formatted Serial Monitor summary - a "report card" that prints all key metrics when the user types R into the Serial Monitor (links to Term 2 Week 3 Serial input).
### 4. SHOWCASE & DEBRIEF
17. Each pair does a 90-second preview demo. The facilitator asks: "Where is the math?" Pair must point to a number on the Serial Monitor, a calculation in the code, or a graph - not just describe it verbally.
18. Peer Review debrief: facilitator asks "What was the most useful piece of feedback you received? What change did you make?" Two pairs share. Class evaluates: was the feedback specific and evidence-based?
19. Design Brief checklist review: facilitator checks 2 briefs publicly against the DDD Written Design Brief rubric (Part 8.5) - not to score, but to calibrate. "This section scores 3 because… To reach 4 it would need…"
20. Demo Day briefing: explain exactly what happens next week - 5-minute presentation, panel of 2, live demo required, questions from panel. Read the DDD Part 8.6 rubric criteria aloud. "This is the rubric you will be scored against."
21. Collect completed Design Briefs (all 7 sections) and peer review rubrics received as this week's artifact and Written Design Brief submission.

## Assessment

- Evidence Required
- Formative (During)
- Working prototype responds to at least one input, produces measurable output, and incorporates THREE Term 2 concepts. Test Record Sheet has 5 rows with specific actions taken for failures.
- Facilitator observation log. 90-second preview demo - "Where is the math?" must be answered concretely.
- Term 2 Week 7 Artifact + Design Brief
- Completed 7-section Design Brief (all sections, pseudocode in How It Works, quantified math element, 5 test results, 2 documented improvements). Peer Review Rubric received from partner. BOTH submitted together. Design Brief also counts as DDD Part 8.5 (10% of total).
- Design Brief + Peer Review Rubric collected and filed. Facilitator scores against DDD Part 8.5 rubric (completeness 4% + English clarity 3% + math accuracy 3%).
- Differentiation
- Support: reduce to TWO Term 2 concepts; provide a pre-written How It Works pseudocode template with blanks. Extension: Serial Monitor "report card" feature; third documented improvement based on self-assessment against DDD rubric.
- Extension: R-command report card tested and documented in Design Brief.

## Safeguarding

Project topics must be approved by the facilitator before building begins - ensure no project involves monitoring, recording, or classifying other people without consent. The peer review process must be structured and supervised: facilitators read all written peer feedback before it is exchanged to check for inappropriate comments. Remind learners: peer review is a professional practice - feedback must be about the work, never about the person.

ILO 3.4 (summative) - Design, build, test, iterate, and present an original Arduino project that integrates at least one coding concept, one explicit English literacy connection, and one explicit Mathematics connection, supported by a written design brief (DDD Part 8.5).
In Term 1 you built something that worked. In Term 2 you build something that works, is documented, is tested, has been peer reviewed, and connects computing to English and Mathematics - by design, not by accident. That is the difference between a project and an engineering artefact.
English Literacy Thread
Mathematics Thread
Design Brief as an engineering document: the 7 sections escalate in register and demand from term to term. The Term 2 brief requires a How It Works section written as pseudocode first, then translated to code - establishing that the natural language description precedes and controls the code, not the other way around. The Improvements Made section must document each change as: "Original design: [X]. Problem identified: [Y]. Change made: [Z]. Result: [W]." This is a formal revision history - a real engineering practice. Peer Review: written feedback must be evidence-based ("The code quality criterion requires comments on every function - I can see that readTemperature() has comments but announceClass() does not").
Every project must demonstrate one quantified mathematical element in its output - not just described in the brief. Acceptable options: (1) rolling mean of 5 sensor readings printed to Serial Monitor, with mean and range displayed; (2) arithmetic sequence generated by a for loop, with first term, common difference, and nth term calculated and printed; (3) classification accuracy calculated from test results ((passed ÷ 5) × 100%); (4) two-dataset comparison with percentage difference between means. The mathematical element must be visible during the Demo Day presentation - it must appear on screen, on a graph, or in a printed output.
