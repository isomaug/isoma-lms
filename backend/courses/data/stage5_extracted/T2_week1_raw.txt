Distribute the Term Two Entry Review quiz. Learners complete individually in silence (5 min). Questions recap: (1) Name 3 Arduino data types. (2) Write the syntax for a for loop from 1 to 10. (3) What does Serial.println() do? (4) Name one comparison operator. (5) What is an if/else condition used for? Pairs swap and peer-mark (facilitator reads answers aloud).
Quick-fire class recap: facilitator points to a Term One concept on the board and asks a learner to explain it in one sentence. Rotate through 6 concepts: variable, loop, condition, function, sensor, array.
Introduce Term Two framing: "Everything you learned in Term One was a single tool. This term, we combine those tools to build bigger things. Today we learn how to organise those tools properly — that is called code architecture."
Show two versions of the same programme on the projected screen: Version A — all code in loop(), no functions, 40 lines. Version B — same behaviour, decomposed into 4 functions, each 5–8 lines. Ask: "Which is easier to read? Which would be easier to fix if something broke? Which is the better code?"
Facilitator live-codes on the projected screen — pause at each new concept. Start with a review function: void blinkOnce() { digitalWrite(13, HIGH); delay(500); digitalWrite(13, LOW); delay(500); }. Call it from loop(). Learners follow on their own sketches.
Add a parameter: modify to void blinkTimes(int n) { for(int i = 0; i < n; i++) { blinkOnce(); } }. Call with blinkTimes(3) and blinkTimes(7). Ask: "What changes when we change the number? What stays the same?" Link to mathematics: "n is the input, the LED behaviour is the output. This is a function in the mathematical sense."
Return values: write int readButton() { return digitalRead(2); }. Use in loop(): if(readButton() == HIGH) { blinkTimes(5); }. Explain: "This function goes out, gets a value, and brings it back. Like a messenger — it does one job and returns with the answer."
Architecture map task: distribute the printed 25-line sketch. Pairs read the entire sketch and fill in the architecture map worksheet: every function listed, its purpose in one plain-English sentence, its inputs (parameters), and its outputs (return value or side effect).
Annotation task: using the wide right margin of the printed sketch, annotate every function declaration and every significant line with a plain-English comment. Must be complete sentences.
Rotate Driver/Navigator. New driver now leads the debug challenge.
Debug challenge: distribute the printed debug sketch. Pairs identify all 3 architectural errors on paper first (without uploading). Errors include: function called before it is declared, function declared with wrong return type (void instead of int), function call missing a required parameter. Write the fix for each error in the margin.
After finding all 3 on paper, type the corrected version in Arduino IDE and upload to confirm it compiles and runs. If any error remains, trace line by line.
Composition challenge: write a new sketch from scratch with at least 3 named functions addressing a real scenario. Suggested scenarios (pair chooses one): a door alarm (button pressed = blink + delay pattern); a Morse code sender (blink short and long); a traffic light sequence (3 LEDs or 3 delays representing red/yellow/green). Each function must have a clear, single job. No function should be longer than 10 lines.
Facilitator circulates. Prompt: "Can you explain what each function does in one sentence? If not, it might be doing too many things." Observe participation and note on participation log.
Extension: write a function int countButtonPresses(int seconds) that counts how many times the button is pressed within a given number of seconds and returns that count. Print the result to Serial Monitor.
2–3 pairs demonstrate their composition challenge sketch. As the LED demonstrates the behaviour, the learner reads aloud the function names: "First the setup() runs. Then loop() calls trafficRed() for 5 seconds, then trafficYellow() for 2 seconds, then trafficGreen() for 5 seconds."
Facilitator asks each presenting pair: "If I asked you to change the duration of the red light only, which exact line would you change? How long would it take you to find it?" Demonstrate that well-structured code answers this question instantly.
Connect decomposition to English: "A well-organised essay and a well-organised programme follow the same rule: one idea or one job per section. Your introduction does not contain your conclusion. Your blinkTimes() function does not read the button."
Connect to mathematics: "We defined int doubleValue(int x) { return x * 2; }. In mathematics, that is written f(x) = 2x. The equals sign and the return statement are the same idea expressed in two different languages."
Exit question (written on architecture map reverse): "Describe decomposition in two sentences using an everyday example that is NOT a computer programme." Collect as formative evidence.
Submit annotated sketch, architecture map, and debug challenge via USB flash drive.

CROSS-CURRICULAR LINKS
English | Decomposition as essay structure: facilitator explicitly draws the parallel between organising a programme into functions and organising an essay into paragraphs. Each function has a single job — like each paragraph has a single main idea. The architecture map requires learners to write a purpose statement for each function in plain English (a full sentence). The annotation task is treated as a technical writing exercise: comments must be complete sentences in the correct tense ("This function makes the LED blink n times.").
Maths | Functions as mathematical input-output machines: blinkTimes(int n) is a function f(n) — given n, produce a result. Return values make this explicit: int doubleValue(int x) { return x * 2; } is f(x) = 2x written in code. Modular arithmetic connection: if a loop runs inside a function every 500ms, how many times does it run in 1 minute? (60000ms ÷ 500ms = 120 iterations.) Link to P6 mathematics: expressing a relationship between two quantities.
