Demonstrate the problem (5 min): load a delay()-based sketch onto the Arduino: LED blinks with delay(2000). Connect a push button. Ask: "Press the button while the LED is in the delay phase." Nothing happens — the button press is ignored. "Why?" Because delay() pauses the entire programme — no inputs are read, no sensors polled, no Serial commands processed. "What kind of real device would be dangerous if it behaved this way?" (Brake system, smoke alarm, medical monitor.)
Distribute the Non-Blocking Timing Diagram. Walk through it: "The top timeline shows delay()-based: during the 2-second delay, the entire programme is frozen — no button, no sensor, no Serial. The bottom timeline shows millis()-based: the LED state is toggled at the right time, but the main loop keeps running continuously. At every point in the millis() timeline, inputs can be read."
Introduce millis() syntax on the board: unsigned long currentTime = millis(); unsigned long elapsed = currentTime - lastToggleTime; if(elapsed >= interval) { /* toggle LED */ lastToggleTime = currentTime; }. Learners copy with plain-English annotations for each line.
Introduce struct syntax: "A struct is a custom data type — it bundles related variables into one named unit. Instead of int led1Pin, bool led1IsOn, unsigned long led1LastTime — we write struct LED { int pin; bool isOn; unsigned long lastToggleTime; long interval; }; and create one variable LED myLed; that holds all four values together."
Single LED non-blocking sketch (15 min): facilitator live-codes. Declare: const int ledPin = 9; bool ledState = false; unsigned long lastToggle = 0; long blinkInterval = 500; In loop(): unsigned long now = millis(); if(now - lastToggle >= blinkInterval) { lastToggle = now; ledState = !ledState; digitalWrite(ledPin, ledState); } Serial.println(millis()); Upload. Observe Serial Monitor: numbers increase continuously — the loop never pauses. Now press the push button: the programme responds instantly even during the LED blink cycle.
Verify non-blocking: "Count the Serial Monitor lines during one 500ms blink interval. How many times did the loop run?" (Hundreds of times.) "With delay(500), how many times would the loop run?" (Exactly once.) Pairs record the answer on the struct worksheet.
Struct definition and instantiation (15 min): facilitator adds the struct above setup(). struct LED { int pin; bool isOn; unsigned long lastToggleTime; long interval; }; Create 3 instances: LED leds[3]; In setup(), initialise each: leds[0] = {9, false, 0, 200}; leds[1] = {10, false, 0, 500}; leds[2] = {11, false, 0, 1000}; pinMode for each pin. Upload and confirm all 3 LEDs blink at their own rates.
Unified update loop (15 min): in loop(): unsigned long now = millis(); for(int i = 0; i < 3; i++) { if(now - leds[i].lastToggleTime >= leds[i].interval) { leds[i].lastToggleTime = now; leds[i].isOn = !leds[i].isOn; digitalWrite(leds[i].pin, leds[i].isOn); } } Serial.println(now); Upload. Observe: 3 independently blinking LEDs driven by a 3-line for loop. Ask: "What would change if we added a 4th LED? How many lines of code would that require?" (Only 1 more initialisation line — the for loop handles it automatically.)

English | Technical comparison document writing: the 120-word comparison across 4 criteria is structured technical prose — not a list. Each criterion must be addressed in a full paragraph that contrasts both approaches and states a real-world implication. "In terms of responsiveness, delay()-based timing freezes the entire programme for the duration of the delay. This means a programme cannot respond to any input — sensor, button, or Serial command — while a delay is running. A medical heart rate monitor that used delay() would miss a pulse if the delay interval exceeded the measurement window. millis()-based timing, by contrast, allows the main loop to run continuously…" This type of writing — comparative, criteria-based, with real-world application — is the foundation of technical reporting and evaluative essays at secondary level.
Maths | Elapsed time as a continuous variable: millis() returns an unsigned long representing the number of milliseconds since the Arduino last reset. unsigned long elapsed = millis() - lastToggleTime; is a subtraction of two timestamps — the mathematical operation of finding the duration between two points on a continuous time axis. LCM calculation: if LED 1 blinks every 200ms, LED 2 every 500ms, LED 3 every 1000ms — when do all three first toggle simultaneously? LCM(200, 500, 1000): factor 200 = 2³ × 5²; factor 500 = 2² × 5³; factor 1000 = 2³ × 5³. LCM = 2³ × 5³ = 1000ms. Learners verify: does the Arduino output show all 3 LEDs toggling at exactly t=1000ms, t=2000ms, t=3000ms? Proportional reasoning: if LED 3's interval is doubled to 2000ms, the new LCM becomes LCM(200, 500, 2000) = 2000ms.
