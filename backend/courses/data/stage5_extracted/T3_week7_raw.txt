Brief reflection requirement (5 min): each learner writes on a sticky note — "My Term Two project: one thing it demonstrated well, one technical limitation, one specific way the capstone addresses that limitation." This sticky note is attached to the design brief inside cover. It is not graded but is read by the peer reviewer.
Project selection and feasibility (10 min): pairs propose one project idea naming the real-world problem, the target user, and the three T3 concepts it will use. Facilitator evaluates feasibility against the component kit and the 3-session time budget. Any project requiring components not in the kit is revised before proceeding. Facilitator approval is mandatory before any brief writing begins.
Algorithm-first design (20 min): before Sections 1–7 of the brief, write the pseudocode algorithm and flowchart on the algorithm paper. The algorithm must cover the full programme logic: sensor reading, statistical update, classification or alert, Serial command handling, and output. Facilitator approves the algorithm before any brief writing or circuit sketching begins. "If I cannot approve the algorithm, the design brief cannot proceed. The algorithm is the source of truth."
Design brief Sections 1–7 (15 min): complete all 7 standard sections. Section 4 (How It Works) must reference the pseudocode by line number: "Step 3 in the pseudocode — read both sensors — is implemented in the takeReading() function." The Components List (Section 5) must specify every component, resistor value, and pin number.
Design brief Sections 8–10 (10 min): Section 8 — Reflection on Term Two (minimum 4 sentences: what was built, what it demonstrated, its limitation, how this capstone addresses it). Section 9 — T3 Concept Integration (minimum 3 concepts, one sentence each explaining the specific technical contribution). Section 10 — Algorithm Documentation reference (confirm that the approved pseudocode and flowchart are attached and that every pseudocode step is numbered for cross-referencing in the code).
Circuit sketch on squared paper (10 min): draw the full circuit before touching any component. Label every pin, every resistor value, every component. Pair checks against the component reference card. Facilitator approves the circuit sketch — checking specifically that the LDR voltage divider is correct and that no LED is connected without a resistor. Build begins only after facilitator approval.
Circuit build (15 min): following the approved circuit sketch, assemble on the breadboard. Facilitator verifies every build before USB connection. Check: correct TMP36 orientation, correct resistor values, all jumper wires fully seated, no components bridging adjacent rails unintentionally.
Sketch writing (25 min): open Arduino IDE. Write the full sketch from scratch following the numbered pseudocode steps — every major pseudocode step produces a comment: // PSEUDOCODE LINE 4: Read LDR and compute normalised score. The sketch must include: at least one struct definition and array, millis()-based non-blocking timing, Serial command handling (at minimum START and REPORT), and at least one function that returns a value. No copying from previous weeks' sketches — all code is written from the algorithm.
Test Cycle 1 (10 min): upload and run. Record against the Cycle 1 acceptance criterion: does the programme respond to START and produce correct sensor readings within ±5% of a hand-measured reference? Record the expected value, the actual Serial Monitor output, and the status. If Partially Met or Not Met, document the specific change that will be made before Cycle 2.
Test Cycle 2 (10 min): implement the change from Cycle 1. Upload and run. Record against the Cycle 2 criterion: after 20 readings, does the printed running mean match the hand-calculated mean within ±0.01? Record expected, actual, and status. If the mean is correct, calculate and record the percentage deviation that triggered the most recent alert.
Test Cycle 3 (10 min): test the AI classification or alert element. Run 10 inputs through the classifier (manually set conditions, or use the Serial command interface). Record the true class for each and the predicted class. Calculate: accuracy = correct ÷ 10. Record in the Test Results section of the brief. If accuracy is below 70%, identify the most common misclassification and propose a specific threshold adjustment that would address it.
Code review self-assessment (5 min): apply the 6-criterion code review rubric from T3 Week 1 to the learner's own sketch. Score every criterion honestly — facilitated by the reminder that the peer reviewer will also score it and significant discrepancies must be discussed. A self-score of 4 requires at least one line of evidence (e.g. "I scored 4 for Comments because every function has a // PSEUDOCODE LINE N: cross-reference and a plain-English purpose statement").
Peer review (15 min): swap the full submission package (design brief, algorithm paper, acceptance criteria log, code review self-assessment) with a partner pair. Apply the 8-question peer review rubric. Q8 is new: "Does the code review self-assessment appear honest? If you disagree with any self-score, cite the specific criterion and the specific evidence." Return with feedback. Read and initial receipt.
Presentation rehearsal (10 min): each learner delivers the 5-minute structure to their partner: Problem → Algorithm (hold up and briefly explain the flowchart) → Live Demo → Statistical Evidence (state one quantitative result from the test cycles) → Reflection (Term One to Term Three growth in one clear sentence per term). Partner gives 1 Star + 1 Wish. Facilitator listens to at least 2 rehearsals.
2 pairs give a full presentation rehearsal (5 minutes each). Class observes and completes Questions 1–4 of the peer review rubric for the presenter as Demo Day preparation practice.
Facilitator gives whole-class feedback targeted at three dimensions: (1) Algorithm-to-code link: "I checked 4 design briefs. 3 have the pseudocode cross-references in the code comments. 1 does not — add them before Demo Day. The panel will look for this." (2) Test cycle quantitative results: "Every test results section must contain at least one number with a calculation. A status of 'Met' without a number is not evidence — it is an assertion." (3) T3 concepts: "Section 9 of your brief must name three T3 concepts with a technical explanation. 'I used a struct' is not sufficient — 'The struct bundles the sensor id, normalised ldr value, temperature, and timestamp into a single array element, allowing all 50 readings to be managed with a single for loop' is the standard required."
Facilitator confirms Demo Day logistics for all 8 learners: panel composition (facilitator + invited assessor), presentation order (announced), timing (5 minutes + 3 minutes Q&A), submission requirements (design brief, annotated sketch, acceptance criteria log, algorithm paper, all submitted before the presentation begins).
Remind learners of the assessment weights from DDD Part 8: Participation 10%, Weekly Artifacts 25%, Prototype Functionality 10%, Code Quality 10%, Integration 10%, Presentation 20%, Written Design Brief 10%, Peer Review 5%. CROSS-CURRICULAR LINKS
English | The 10-section design brief is the definitive technical writing artifact of the programme. Section 8 (Reflection on Term Two Project) must be analytically comparative — not just "my Term Two project was a traffic light FSM." It must state: what the FSM could do that a simple if/else could not; what limitation the FSM still had; how the capstone project addresses that limitation. Section 9 (T3 Concept Integration) must name each of the three (or more) T3 concepts with a one-sentence technical explanation of its specific contribution: "The struct array stores all sensor readings with their timestamps — without the struct, we would need 50 separate variables for each field, which would be unmanageable." Section 10 (Algorithm Documentation) is new in T3: it links the written design to the pseudocode. The peer reviewer in T3 checks that every major pseudocode step appears as identifiable code — bridging the written and implemented dimensions of the design.
Maths | Three documented test cycles require quantitative results. Cycle 1 verifies basic functionality: does the system produce correct sensor readings within ±5% of a hand-measured reference value? Cycle 2 tests the statistical computation: after 20 readings, is the printed running mean within ±0.01 of the hand-calculated mean? Cycle 3 tests the AI/classification element: if the system has a classifier, run 10 test inputs and calculate accuracy. Record: correct ÷ 10 = accuracy %. If the system has a deviation alert, record the number of alerts triggered in a 5-minute logging session and calculate alerts per minute as a rate. Every number in the test results section must have a calculation with working shown — consistent with the standard established in T1 W5, T2 W5, and T3 W4–5.
