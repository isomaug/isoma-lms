# Week 5 - Lesson 2

## Session length
**About half of this week's plan** (finish what you started in Lesson 1)

## Finish the week
- Design and write a DataReading struct with fields: int id, float ldrNorm, float tempC, unsigned long timestamp, String label — and declare an array of 50 such structs as the programme's data store
- Write a complete data logger programme using millis()-based non-blocking timing that: reads both sensors every 5 seconds, stores each reading into the struct array, computes live running statistics (mean, min, max, range) for both ldrNorm and tempC after each new reading, and prints a formatted data log line to Serial Monitor
- Implement Serial command control: "START" begins logging, "STOP" pauses logging, "REPORT" prints the full statistics summary, "RESET" clears the array and resets all statistics — all without blocking the timing loop
- Calculate the percentage deviation of each new reading from the current running mean: deviation = ((newValue − currentMean) ÷ currentMean) × 100.0 — print an alert to Serial Monitor if deviation exceeds 20%
- Write a full Technical System Documentation Report (minimum 150 words) structured as: System Overview | Hardware Components | Software Architecture (function list with one-sentence description each) | Statistical Methods Used | Sample Output (transcribed from Serial Monitor) | Limitations and Improvements
- Evaluate the programme against 4 self-defined acceptance criteria written before coding begins — confirming each criterion as Met, Partially Met, or Not Met with evidence from the live output

### INDEPENDENT WORK — REPORT Function, Graph, and Documentation  (50 min)
1. Acceptance criteria evaluation (10 min): test the programme against each of the 4 acceptance criteria written in the warm-up. For each criterion: confirm it as Met, Partially Met, or Not Met with specific evidence (e.g. "Criterion 1 — Met: Serial Monitor shows running mean updated after every reading, verified against hand calculation for readings 1, 5, and 10"). 2. Time-series graph (10 min): from the transcribed Serial Monitor data, plot ldrNorm and tempC (normalised to 0.0–1.0 by dividing by 40.0) on the same time axis on squared paper. Use two different coloured lines. Label both axes, add a title, add a legend distinguishing the two lines. Identify and annotate any point where the deviation alert was triggered.
3. Technical System Documentation writing (15 min): write the full 6-section report. Each section must be complete. The Software Architecture section lists every function with a one-sentence description. The Statistical Methods section explains the running mean formula and why it is more efficient than recalculating from the full array each time. The Limitations section must be honest and specific with at least 2 named limitations including the 50-reading cap calculation.
4. Check your work carefully. Ask: "What is the purpose of the RESET command in a deployed system? What would happen if the struct array fills up without a reset mechanism?" Note participation.
5. 2–3 you do a live demonstration: type "START", wait for 3 readings, type "STOP", type "REPORT". Project the Serial Monitor. Class verifies: does the mean update with every reading? Does the min/max track correctly? Is the deviation alert firing at the right threshold?

Criterion 4 — Not Met: we did not implement the label field in the struct; all labels are empty strings." Discuss: "Is 'Partially Met' a pass or a fail? What action does it require?"

### SHOWCASE & DEBRIEF  (30 min)
7. Connect to professional engineering: "What you built today is called a data acquisition system. Every IoT device — smart electricity meters in Kampala, weather monitoring stations, medical monitors — has exactly this architecture: sense, store, compute, report, respond to commands. The difference between your logger and a commercial one is scale: they use more sensors, larger storage, and a network interface instead of Serial. The architecture is identical."
8. Remember English link: "Technical System Documentation is what engineers write so that someone else can maintain their system five years after they built it. The test of good documentation is: could a competent engineer who has never seen this programme understand exactly what it does, how it is structured, and where to find each function by reading only your document?"
9. Remember Math link: "Running statistics are mathematically equivalent to batch statistics — same result, different computation path. The running mean formula ((prevMean × (n−1)) + newValue) ÷ n is O(1) per update — it takes constant time regardless of n. Recalculating from the full array is O(n) — it gets slower as n grows. You chose the more efficient algorithm without knowing it. That is called algorithmic thinking applied to statistics."
10. Exit question (written): "Name one limitation of your data logger that would prevent it from being used in a professional deployment, and propose a specific technical solution." Collect.

## Stay safe
Safeguarding Note: All data collected by the logger is environmental data (light and temperature) — no personal biometric or identifying data. Remind you that the RESET command permanently destroys all stored readings — in a real system, a confirmation prompt would prevent accidental data loss. Serial Monitor output may be visible to others using the same laptop — you should not type personal information into Serial command inputs. The deviation alert buzzer should be tested briefly only — sustained alerts in a small room can cause discomfort for you with auditory sensitivity.
