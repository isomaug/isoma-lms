# Lesson T3–3: Algorithm Design from Problem Statements — From Brief to Blueprint

**Duration:** 3 hours (Saturday) / 90 min × 2 days (Holiday) (split across Week 3 Lesson 1 start + Lesson 2 finish)
**Term / Week:** Term 3 · Week 3
**Age Range:** 10–12 years
**Group Size:** 8 learners (pair programming, 4 pairs)
**Hardware:** Arduino Uno, USB cable, laptop with Arduino IDE 2.x, LDR (pin A0), TMP36 (pin A1), buzzer (pin 8), 2 LEDs (pins 9, 10), 220Ω resistors × 2, 10kΩ resistor, breadboard, jumper wires
**Bloom's:** L5 Evaluating → L6 Creating
**DDD ILO:** ILO 3.2 – Apply variables, functions, and loops to solve mathematical problems computationally; extend to designing original algorithms from a written problem specification, expressing them in pseudocode and flowcharts before writing any code. ILO 3.4 – Design and build original Arduino projects; apply algorithm design as the pre-coding step for all programme work.
**NCDC:** Uganda NCDC P5–P6 – English Strand: Analytical reading of problem specifications, technical writing of algorithm documentation, structured argument for design decisions; ICT Strand: Algorithm design, flowchart notation, pseudocode, stepwise refinement, correctness proof by tracing; Mathematics Strand: Algorithm efficiency, worst-case and best-case analysis, threshold optimisation
**Cambridge:** Cambridge Primary Computing 0845 – Stage 5: Designing algorithms; expressing algorithms in pseudocode and flowcharts; evaluating algorithm correctness and efficiency; computational thinking at the design stage

**Big Idea:** An algorithm is a precise plan written before you touch the keyboard. Every professional programme starts with an algorithm. Code without an algorithm is like building a house without a blueprint — it might stand, but it will not be what was intended.

**Context:** Term Two Context: Terms One and Two both had learners write "How It Works" pseudocode as part of a design brief. Term Three Week 3 makes algorithm design the full session focus — not a subsection of a larger task. Learners receive a problem specification and must produce a complete algorithm (pseudocode + flowchart + correctness trace + efficiency analysis) before writing a single line of Arduino code. This mirrors professional software engineering practice and prepares learners for the capstone project in T3 Weeks 7–8 where they must design an algorithm for an original, complex system.

## Learning Objectives

- Read a problem specification and decompose it into named sub-problems, each of which maps to a function in the final implementation
- Write a complete pseudocode algorithm for a given problem specification — using standard pseudocode conventions: WHILE, FOR, IF/ELSE, SET, INPUT, OUTPUT, CALL — with enough detail that a partner could implement it without seeing the specification
- Draw a flowchart for the same algorithm using correct notation: oval (start/end), rectangle (process), diamond (decision), arrow (flow)
- Trace through the pseudocode with at least 2 distinct input scenarios and record the expected output for each — proving the algorithm is correct before any code is written
- Implement the algorithm in Arduino code, mapping each pseudocode line to one or more lines of code with a comment linking them: // Pseudocode line 7: IF temperature > threshold
- Evaluate the algorithm's efficiency: identify the best case (fewest decisions reached), the worst case (most decisions evaluated), and propose one optimisation with a justification

## Materials and Preparation

- 4 laptops with Arduino IDE 2.x
- 4 Arduino Uno boards + USB cables, LDR, TMP36, buzzer, 2 LEDs, resistors, breadboard, jumper wires
- Printed "Problem Specification Cards" (A5 per pair) — 3 different problem specifications of increasing complexity, each 6–8 lines long, written in plain English
- Printed "Pseudocode Convention Reference Card" (A5 per pair) — 8 pseudocode keywords with syntax examples: SET, INPUT, OUTPUT, IF/ELSE/ENDIF, WHILE/ENDWHILE, FOR/ENDFOR, CALL, RETURN
- Printed "Flowchart Template" (A4 per pair) — pre-drawn oval start/end nodes and blank rectangle/diamond shapes to complete
- Printed "Algorithm Trace Table" (A4 per pair) — columns: Step | Variable values | Output | Decision taken
- Printed "Algorithm Efficiency Evaluation" (A5 per learner) — two rows: Best Case / Worst Case with decision count and justification space
- USB flash drives
- Facilitator device + projected screen

## Cross-Curricular Links

**English:** Pseudocode as a formal writing register: pseudocode uses a fixed vocabulary (SET, IF, WHILE, CALL, RETURN) that is more constrained than natural language but less constrained than code syntax. Writing correct pseudocode requires precision — every variable must be named before it is used, every decision must have both branches, every loop must have a clearly stated termination condition. Reading a problem specification and translating it into pseudocode is an act of analytical reading: "What inputs does the problem describe? What outputs are required? What decisions must be made? What repeats?" These are comprehension questions applied to a technical document. The flowchart is a visual representation of the same algorithm — learners must produce both and confirm they agree. A pseudocode and flowchart that contradict each other indicate an ambiguity in the algorithm that must be resolved before coding.

**Maths:** Algorithm efficiency analysis at an accessible level: the best case is the scenario where the algorithm terminates fastest (fewest decisions, fewest loop iterations). The worst case is where it terminates slowest. For a search algorithm: best case — target found at index 0 (1 comparison); worst case — target at last index or not found (n comparisons for an array of n elements). This introduces O(n) complexity informally. Threshold optimisation: the classification thresholds (e.g. temperature > 28°C for "hot") affect how often each branch is taken. A threshold set too low means the "hot" branch is taken almost always — making the "cool" branch effectively dead code. Learners calculate: if the temperature sensor returns values between 23°C and 35°C in a typical Kampala classroom, what threshold value divides the dataset most evenly? Answer: the median of the range = (23+35)÷2 = 29°C.

## Lesson Structure

### WARM-UP & REVIEW — Algorithms Before Code  (20 min)
1. Open with a question: "Imagine you want to bake a mandazi. Do you start by lighting the fire and then decide what ingredients to use? Or do you plan the recipe first?" Algorithms are recipes. Code is the cooking. "Every programme you have written this year was based on an algorithm — but in Terms One and Two, you wrote the algorithm informally, as numbered steps in a design brief. Today you write algorithms formally, using an internationally recognised notation."
2. Introduce the pseudocode convention reference card. Facilitator models translating one sentence of English into pseudocode on the board: "The programme reads the temperature and if it is above 28°C it turns the buzzer on." → SET temperature TO INPUT(A1) / IF temperature > 28 THEN / OUTPUT(buzzer, ON) / ELSE / OUTPUT(buzzer, OFF) / ENDIF. Learners annotate the reference card with the example.
3. Introduce flowchart symbols (3 min): oval = start or end; rectangle = process (SET, OUTPUT, CALL); diamond = decision (IF, WHILE); arrow = direction of flow. Draw a 4-node example on the board. Learners copy.
4. Problem specification distribution: give each pair the Specification Cards. "Read all 3 specifications. Choose the one your pair will work on. Each specification describes a real-world sensing problem. You must design the algorithm — not code it — in the first half of this session."
5. Decomposition (10 min): pairs read their chosen specification and identify the sub-problems. Write these as function names on the pseudocode sheet: e.g. READ_SENSORS(), CLASSIFY_ENVIRONMENT(), TRIGGER_OUTPUT(), LOG_TO_SERIAL(). Facilitator checks: "Does every sub-problem have a single, clear job? Could you explain each function's purpose in one sentence?"
6. Pseudocode writing (20 min): using the convention reference card, pairs write the full pseudocode for their chosen specification. Every variable must be named before use. Every IF must have an ELSE. Every WHILE must have a condition that can become false. Every sub-problem function must appear as a CALL statement in the main algorithm. Facilitator circulates: "Can I understand what this algorithm does without reading the specification? Is every decision explicit?"

### GUIDED ACTIVITY — Pseudocode, Flowchart, and Trace  (60 min)
7. Flowchart drawing (10 min): translate the pseudocode into a flowchart on the printed template. Every diamond must have two labelled arrows (YES/NO or TRUE/FALSE). The flow must start at the start oval and end at the end oval with no dangling arrows.
8. Algorithm trace (20 min): using the trace table, pairs trace through the pseudocode for TWO distinct input scenarios. Scenario 1: LDR reads 750 (bright), temperature reads 31°C. Scenario 2: LDR reads 200 (dark), temperature reads 24°C. For each scenario, fill in every row of the trace table: Step number, variable values at that step, any output triggered, decision taken at each diamond. Confirm: does the algorithm produce the correct output for both scenarios? If not, identify the error and correct the pseudocode before proceeding.
9. Arduino implementation (25 min): translate the verified pseudocode into an Arduino sketch. Every pseudocode line must have a corresponding comment in the code: // PSEUDOCODE LINE 5: IF temperature > threshold. Every function named in the pseudocode becomes a named void function in the sketch. Upload and test with the physical circuit. Verify: does the hardware behave as predicted by the trace table for both scenarios?
10. If the hardware behaviour differs from the trace prediction: do not change the code first — revisit the pseudocode. Find which pseudocode line produced the discrepancy and correct it there first. Then update the code. "The algorithm is the source of truth — not the code."
11. Efficiency evaluation (15 min): complete the algorithm efficiency evaluation worksheet. Best case: which scenario causes the algorithm to take the fewest steps? Count the exact number of decisions made and state the specific input values that produce this case. Worst case: which scenario causes the most decisions? Count and state. Optimisation proposal: identify one place in the algorithm where two IF statements could be merged into one compound condition (&&/||) without changing the output. Write the optimised pseudocode line and calculate the reduction in decision steps.

### INDEPENDENT WORK — Implementation and Efficiency Evaluation  (50 min)
12. Threshold calculation (10 min): for the temperature threshold in the specification, calculate the median-based optimal threshold: range = max recorded − min recorded; optimal threshold = min + (range÷2). If the specification uses a different threshold, evaluate: is the chosen threshold above or below the median? Who or what is disadvantaged by this choice? (Link to the bias concept from T2 Week 6.)
13. Facilitator circulates. Ask: "If someone handed you only the flowchart, could they implement this programme correctly without seeing the specification? If not, what is missing from the flowchart?"
14. 2–3 pairs present their algorithm — not their code — to the class. They show the flowchart on the projected screen and walk through it for Scenario 1, narrating each step: "The algorithm starts here. It reads the sensors. The temperature is 31°C — greater than the threshold of 28. So the YES branch is taken. The buzzer is activated. The algorithm then checks the light level…"
15. Class peer-review of the presented flowchart: "Is every diamond labelled with a YES and a NO branch? Is there a path that reaches the end oval? Is there any path that results in an infinite loop?" Identify and discuss any issues found.
16. One pair presents their efficiency evaluation: "The best case for our algorithm is when the temperature is above threshold AND the light is above threshold — both conditions are satisfied on the first evaluation, 2 decisions total. The worst case is when both conditions are below threshold — both branches must be evaluated, 4 decisions. We proposed merging the two IF statements into a single compound condition: IF temp > 28 AND light > 500 — this reduces the worst case to 2 decisions."

### SHOWCASE & DEBRIEF  (30 min)
17. Facilitator draws the connection to professional software development: "In industry, the algorithm design phase — pseudocode, flowchart, trace — happens before any developer opens a code editor. The design document is reviewed, approved, and version-controlled. The code you have written today is the implementation of a design that was already proven correct. That sequence — design, prove, implement — is the engineering standard."
18. Facilitator restates English link: "Pseudocode is a writing register — like formal letters or academic essays, it has rules about vocabulary and structure. You followed those rules today. The ability to express a complex process in formal, unambiguous language is a skill that transfers directly to technical writing, legal drafting, and scientific documentation."
19. Facilitator restates Math link: "Efficiency analysis counts decisions. The best case is the minimum; the worst case is the maximum. Together they define the range of your algorithm's performance — exactly as mean and range define a dataset. You now have a quantitative way to compare two algorithms: which has the smaller worst case? That is a mathematical argument about quality."
20. Exit question (written): "Name one thing your algorithm does correctly and one thing that could be improved. Be specific — name the pseudocode line." Collect.
21. Submit pseudocode, flowchart, trace table, efficiency evaluation, and Arduino sketch via USB flash drive.

## Assessment

- Formative | (During) | Decomposition: sub-problems named as functions before pseudocode writing begins — facilitator check during guided phase | Pseudocode: complete, uses correct conventions, every IF has ELSE, every WHILE has termination condition (checked during guided phase) | Algorithm trace: both scenarios traced correctly, any discrepancy corrected in pseudocode before coding (collected) | Exit question: one specific correct strength and one specific improvement identified (collected)
- Exit Assessment | Pseudocode: complete algorithm using correct conventions, decomposed into named sub-problems, submitted (assessed on 5-point artifact rubric) | Flowchart: correct notation throughout, all paths reach end node, no dangling arrows (submitted) | Arduino sketch: every pseudocode line has a corresponding // PSEUDOCODE LINE N: comment, all named functions implemented, hardware behaviour matches trace prediction (verified by facilitator and submitted) | Efficiency evaluation: best case and worst case step counts calculated with specific input values, one optimisation proposed with pseudocode (submitted) | All materials submitted via USB flash drive
- Differentiation | Support: Reduce to the simplest Problem Specification Card (single sensor, 2 decision nodes). Provide the pseudocode skeleton with function names and IF/ELSE structure already present — learner fills in variable names, threshold values, and output actions. For the flowchart, provide pre-drawn shapes and ask learner to add labels and arrows only. Reduce the trace to one scenario. | Extension: After implementing the original algorithm, redesign it using an event-driven architecture: instead of polling sensors in a loop, use Arduino interrupt functions (attachInterrupt()) for the push button input. Write a comparison pseudocode for both the polling version and the interrupt-driven version. Evaluate: which has the better worst case? Which is more appropriate for a battery-powered device where loop() running continuously would drain the battery? This introduces interrupt-driven programming — a Stage 6 concept.
