**About half of this week's plan** (you will finish in Lesson 2)

- Complete a 10-section written design brief: Sections 1–7 from T2 (Problem Statement, Target User, Solution Description, How It Works, Components List, English/Math Connection, Test Results), Section 8 (Reflection on Term Two Project), Section 9 (T3 Concept Integration — naming at least 3 T3 concepts and explaining how each contributes), Section 10 (Algorithm Documentation — pseudocode and flowchart reference)

- Write an Arduino sketch of at least 60 lines using named functions, annotated with comments linking to the pseudocode (// PSEUDOCODE LINE N:), passing the 6-criterion code review rubric from T3 Week 1 at a score of ≥3/4 on every criterion

- Deliver a 5-minute Demo Day presentation rehearsal: Problem -> Algorithm (show the flowchart) -> Live Demo -> Statistical Evidence -> Reflection (Term One to Term Three growth)

## Big idea
This is the project that demonstrates everything. Not just that you can code — but that you can engineer: plan before building, document as you go, test against evidence, reflect with honesty, and present with authority.

## Links to English and Maths
- **English:** The 10-section design brief is the definitive technical writing artifact of the programme. Section 8 (Reflection on Term Two Project) must be analytically comparative — not just "my Term Two project was a traffic light FSM." It must state: what the FSM could do that a simple if/else could not; what limitation the FSM still had; how the capstone project addresses that limitation. Section 9 (T3 Concept Integration) must name each of the three (or more) T3 concepts with a one-sentence technical explanation of its specific contribution: "The struct array stores all sensor readings with their timestamps — without the struct, we would need 50 separate variables for each field, which would be unmanageable." Section 10 (Algorithm Documentation) is new in T3: it links the written design to the pseudocode. The peer reviewer in T3 checks that every major pseudocode step appears as identifiable code — bridging the written and implemented dimensions of the design.
- **Maths:** Three documented test cycles require quantitative results. Cycle 1 verifies basic functionality: does the system produce correct sensor readings within ±5% of a hand-measured reference value? Cycle 2 tests the statistical computation: after 20 readings, is the printed running mean within ±0.01 of the hand-calculated mean? Cycle 3 tests the AI/classification element: if the system has a classifier, run 10 test inputs and calculate accuracy. Record: correct ÷ 10 = accuracy %. If the system has a deviation alert, record the number of alerts triggered in a 5-minute logging session and calculate alerts per minute as a rate. Every number in the test results section must have a calculation with working shown — consistent with the standard established in T1 W5, T2 W5, and T3 W4–5.

## Let's begin

### SESSION 1 / DAY 1 — Algorithm-First Design and Brief Sections 1–10  (60 min)
1. Brief reflection requirement (5 min): you write on a sticky note — "My Term Two project: one thing it demonstrated well, one technical limitation, one specific way the capstone addresses that limitation." This sticky note is attached to the design brief inside cover. It is not graded but is read by the peer reviewer.
2. Project selection and feasibility (10 min): you propose one project idea naming the real-world problem, the target user, and the three T3 concepts it will use. You evaluates feasibility against the component kit and the 3-session time budget. Any project requiring components not in the kit is revised before proceeding. You approval is mandatory before any brief writing begins.
3. Algorithm-first design (20 min): before Sections 1–7 of the brief, write the pseudocode algorithm and flowchart on the algorithm paper. The algorithm must cover the full programme logic: sensor reading, statistical update, classification or alert, Serial command handling, and output. You approves the algorithm before any brief writing or circuit sketching begins. "If I cannot approve the algorithm, the design brief cannot proceed. The algorithm is the source of truth."
4. Design brief Sections 1–7 (15 min): complete all 7 standard sections. Section 4 (How It Works) must reference the pseudocode by line number: "Step 3 in the pseudocode — read both sensors — is implemented in the takeReading() function." The Components List (Section 5) must specify every component, resistor value, and pin number.
5. Design brief Sections 8–10 (10 min): Section 8 — Reflection on Term Two (minimum 4 sentences: what was built, what it demonstrated, its limitation, how this capstone addresses it). Section 9 — T3 Concept Integration (minimum 3 concepts, one sentence each explaining the specific technical contribution). Section 10 — Algorithm Documentation reference (confirm that the approved pseudocode and flowchart are attached and that every pseudocode step is numbered for cross-referencing in the code).

### SESSION 2 / DAY 2 — Circuit Build, Sketch Writing, and First Test Cycle  (60 min)
6. Circuit sketch on squared paper (10 min): draw the full circuit before touching any component. Label every pin, every resistor value, every component. Pair checks against the component reference card. You approves the circuit sketch — checking specifically that the LDR voltage divider is correct and that no LED is connected without a resistor. Build begins only after you approval.
7. Circuit build (15 min): following the approved circuit sketch, assemble on the breadboard. You verifies every build before USB connection. Check: correct TMP36 orientation, correct resistor values, all jumper wires fully seated, no components bridging adjacent rails unintentionally.
8. Sketch writing (25 min): open Arduino IDE. Write the full sketch from scratch following the numbered pseudocode steps — every major pseudocode step produces a comment: // PSEUDOCODE LINE 4: Read LDR and compute normalised score. The sketch must include: at least one struct definition and array, millis()-based non-blocking timing, Serial command handling (at minimum START and REPORT), and at least one function that returns a value. No copying from previous weeks' sketches — all code is written from the algorithm.
9. Test Cycle 1 (10 min): upload and run. Record against the Cycle 1 acceptance criterion: does the programme respond to START and produce correct sensor readings within ±5% of a hand-measured reference? Record the expected value, the actual Serial Monitor output, and the status. If Partially Met or Not Met, document the specific change that will be made before Cycle 2.
10. Test Cycle 2 (10 min): implement the change from Cycle 1. Upload and run. Record against the Cycle 2 criterion: after 20 readings, does the printed running mean match the hand-calculated mean within ±0.01? Record expected, actual, and status. If the mean is correct, calculate and record the percentage deviation that triggered the most recent alert.
