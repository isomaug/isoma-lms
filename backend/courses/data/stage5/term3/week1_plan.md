# Lesson T3–1: Serial Communication, Code Review & Engineering Standards

**Duration:** 3 hours (Saturday) / 90 min × 2 days (Holiday) (split across Week 1 Lesson 1 start + Lesson 2 finish)
**Term / Week:** Term 3 · Week 1
**Age Range:** 10–12 years
**Group Size:** 8 learners (pair programming, 4 pairs)
**Hardware:** Arduino Uno, USB cable, laptop with Arduino IDE 2.x, LED on pin 13, push button on pin 2, 220Ω resistor, breadboard, jumper wires
**Bloom's:** L4 Analysing → L5 Evaluating
**DDD ILO:** ILO 3.1 – Interpret and write Arduino sketches using Serial communication; extend to bidirectional Serial input/output, Serial.parseInt(), and Serial.readString() to create interactive command-driven programmes. ILO 3.3 – Evaluate the quality of code written by others using a structured code review rubric, applying engineering standards.
**NCDC:** Uganda NCDC P5–P6 – English Strand: Critical reading and annotation of technical text, evaluative writing, constructive critique; ICT Strand: Serial communication protocols, bidirectional data exchange, engineering code standards; Mathematics Strand: Baud rate as a rate-of-change problem, data throughput calculations, timing analysis
**Cambridge:** Cambridge Primary Computing 0845 – Stage 5: Data representation and transmission; reading and evaluating code written by others; applying engineering standards to programme design

**Big Idea:** Every professional engineer reviews other people's code before it is used. Code review is not criticism — it is the engineering standard that keeps systems safe, readable, and improvable. Today you become both author and reviewer.

**Context:** Term Two Context: Terms One and Two used Serial.println() and Serial.print() exclusively for output — sending data FROM the Arduino TO the computer. Term Three Week 1 completes the communication loop: learners now also read data FROM the computer INTO the Arduino using Serial.parseInt() and Serial.readString(). This enables interactive, command-driven programmes. The session also introduces formal code review — the process by which all professional software is evaluated before deployment — using a structured rubric that applies the code quality standards from the DDD assessment framework.

## Learning Objectives

- Write an Arduino sketch that receives a command word via Serial Monitor (e.g. "ON", "OFF", "BLINK") and responds by controlling hardware accordingly using Serial.readString() and String comparison
- Write an Arduino sketch that receives an integer via Serial Monitor using Serial.parseInt() and uses it as a variable (e.g. number of blinks, delay value, LED brightness)
- Calculate baud rate as a data transmission rate: at 9600 baud, how many bits are transmitted per second? How many characters per second (assuming 8 bits per character)? How long does it take to transmit a 50-character String?
- Apply a 6-criterion code review rubric to evaluate a provided 30-line sketch written by a fictional peer, scoring each criterion on a 4-point scale and writing a specific justification for every score
- Rewrite one section of the reviewed sketch to improve it — documenting the specific engineering standard violated and the exact change made
- Write a 100-word code review report summarising the quality of the reviewed sketch: what it does well, what violates engineering standards, and what the highest-priority improvement is

## Materials and Preparation

- 4 laptops with Arduino IDE 2.x
- 4 Arduino Uno boards + USB cables, LEDs, push buttons, 220Ω resistors, breadboards, jumper wires
- Printed "Code Review Rubric" (A4 per learner) — 6 criteria: (1) Decomposition — functions used? (2) Comments — every function and significant line annotated? (3) Variable naming — descriptive names? (4) Data types — correct type for each value? (5) Efficiency — no redundant code? (6) Readability — consistent indentation and spacing?
- Printed "Peer Sketch for Review" (A4 per pair) — a 30-line Arduino sketch written at a plausible learner level, with 4 deliberate violations of the 6 code review criteria embedded (poor variable names, missing comments, redundant code blocks, inconsistent indentation)
- Printed "Baud Rate Calculation Worksheet" (A5 per learner) — stepped calculations for bits/second, characters/second, and transmission time
- Printed "Code Review Report Template" (A5 per learner) — 3-section structure: Strengths | Violations Found | Highest-Priority Improvement
- USB flash drives
- Facilitator device + projected screen

## Cross-Curricular Links

**English:** Code review as critical reading: reading code written by someone else is an act of reading comprehension. The reviewer must understand what the author intended, identify where the writing deviates from the standard, and communicate that finding clearly and constructively. The code review report is a piece of evaluative writing — it must name the specific violation, quote the offending line, and justify the recommended change. This mirrors the skill of annotating a peer essay: "In line 14, the variable is named 'x' — this violates the descriptive naming standard because a reader cannot determine what value it holds without reading 6 more lines of context." The 100-word report must use formal, evidence-based language — not "the code is messy" but "three functions lack comments, making it impossible to understand their purpose without tracing the execution manually."

**Maths:** Baud rate as a rate-of-change problem: 9600 baud = 9600 bits per second. At 8 bits per character (standard ASCII), the character transmission rate = 9600 ÷ 8 = 1200 characters per second. Time to transmit a 50-character String = 50 ÷ 1200 = 0.042 seconds = 42 milliseconds. Why does this matter? A delay(10) in loop() runs every 10ms — faster than the Serial buffer can clear a long String. Learners calculate: at what String length does transmission time exceed 10ms? (10ms × 1200 char/s = 12 characters.) Strings longer than 12 characters should use delay(50) or longer to avoid buffer overflow. This connects rate, time, and data — a P6-level proportional reasoning problem in a real engineering context.

## Lesson Structure

### WARM-UP & REVIEW — Two-Way Communication  (20 min)
1. Term Two recap: "In Terms One and Two, the Arduino talked TO you — it printed values to the Serial Monitor. Today it also listens to you. You can type a command and the Arduino will respond." Demonstrate live: facilitator has a pre-loaded sketch. Types "ON" into the Serial Monitor — LED turns on. Types "OFF" — LED turns off. Types "BLINK" — LED blinks 5 times. Ask: "How do you think this works? What does the Arduino need to be able to do?"
2. Introduce the new functions: Serial.available() — returns the number of characters waiting in the input buffer. Serial.readString() — reads all available characters as a String. Serial.parseInt() — reads the next integer from the buffer. Write syntax on the board. Learners copy with a plain-English annotation for each.
3. Baud rate introduction (5 min): distribute the calculation worksheet. "Baud rate is a transmission speed — how fast data travels between the Arduino and the computer. 9600 baud means 9600 bits per second. Let's calculate what that means in practice." Walk through the first calculation together. Learners complete the remaining rows independently.
4. Bridge to code review: "This term, you are senior AI Engineers. Senior engineers do not just write code — they review each other's code before it ships. Today you learn how to do that professionally, using the same criteria the DDD uses to assess YOUR code on Demo Day."
5. Serial.readString() command sketch (20 min): facilitator live-codes. In setup(): Serial.begin(9600). In loop(): if(Serial.available() > 0) { String command = Serial.readString(); command.trim(); if(command == "ON") { digitalWrite(13, HIGH); Serial.println("LED is ON"); } else if(command == "OFF") { digitalWrite(13, LOW); Serial.println("LED is OFF"); } else if(command == "BLINK") { for(int i=0; i<5; i++) { digitalWrite(13, HIGH); delay(200); digitalWrite(13, LOW); delay(200); } Serial.println("Blinked 5 times"); } else { Serial.println("Unknown command"); } } Learners follow on their own sketches. Upload. Test all 4 commands including an unknown one.
6. Note command.trim() — explain: "When you press Enter in the Serial Monitor, a newline character \n is added. trim() removes leading and trailing whitespace including newline characters. Without trim(), the comparison command == "ON" would fail because the String received is actually "ON\n"." Pairs test: what happens if they remove trim()? Does "ON" still match?

### GUIDED ACTIVITY — Serial Input and Command-Driven Programmes  (60 min)
7. Serial.parseInt() sketch (20 min): new sketch. In loop(): if(Serial.available() > 0) { int blinkCount = Serial.parseInt(); Serial.print("Blinking "); Serial.print(blinkCount); Serial.println(" times"); for(int i=0; i<blinkCount; i++) { digitalWrite(13, HIGH); delay(300); digitalWrite(13, LOW); delay(300); } } Upload. Type 3 → LED blinks 3 times. Type 7 → blinks 7 times. Type 0 → no blinks. Type -1 → what happens? Pairs investigate and document.
8. Rotate Driver/Navigator. Combine both: write a sketch that accepts either a String command ("FAST", "SLOW", "STOP") OR an integer (number of blinks). Use Serial.peek() to decide which parser to call: if the first character is a digit, call parseInt(); otherwise call readString().
9. Distribute the printed "Peer Sketch for Review." Pairs read the full 30-line sketch silently and individually for 3 minutes before discussing. "Before you write anything on the rubric, understand what the sketch is trying to do. What is its purpose? What hardware does it control?"
10. Apply the code review rubric independently: each learner scores all 6 criteria on their own rubric sheet first (before discussing with their pair partner). For every score below 4, they must write a specific justification: quote the line number, name the standard violated, and state what the correct version should look like.
11. Pair discussion: compare scores with partner. Where do scores differ, discuss: "I gave Criterion 2 a 2 because lines 8, 14, and 22 have no comments. You gave it a 3 — why?" Agree on a final score for each criterion and record on one shared rubric.

### INDEPENDENT WORK — Code Review  (50 min)
12. Rewrite task: choose the criterion with the LOWEST score. Rewrite only the lines that violate that criterion. Document: "Original line 14: int x = analogRead(A0); — violates variable naming standard. Rewritten: int lightSensorValue = analogRead(A0); — descriptive name makes purpose clear without reading context." Type the rewritten version in Arduino IDE and confirm it compiles.
13. Write the 100-word code review report on the template: 3 sections — Strengths (what the sketch does well, minimum 2 specific points), Violations Found (every violation found across all 6 criteria, with line references), Highest-Priority Improvement (the single most important change, with full justification).
14. Facilitator circulates. Ask: "If this sketch were your project submitted for Demo Day, which rubric criterion would cost you the most marks? How would you fix it?"
15. 2–3 pairs demonstrate their command-driven sketches: type a command or integer live in the Serial Monitor while the class watches the LED response. Ask: "What happens if you type the command in lowercase? Why does the comparison fail?"
16. One pair presents their code review report. They read aloud the Violations Found section and show the original line alongside their rewritten version on the projected screen. Class discusses: "Do you agree this is a violation? Is the rewrite an improvement? Is there a better solution?"

### SHOWCASE & DEBRIEF  (30 min)
17. Facilitator connects code review to the DDD assessment rubric: "Criterion 2 in the DDD Demo Day rubric is Code Quality: correct variables, loops, functions, and comments. When the panel assesses your project in Week 8, they are applying a code review to your sketch in real time. Today you practised from the reviewer's chair — that knowledge makes you a better author."
18. Facilitator restates English link: "A code review report is a piece of technical writing with a specific professional structure. The same skills — identify, quote, evaluate, recommend — appear in literary criticism, scientific peer review, legal opinion, and journalism. You are practising a transferable analytical writing form."
19. Facilitator restates Math link: "The baud rate calculation is a rates problem. Speed × time = data. At 9600 baud, a 12-character String takes exactly 10 milliseconds. If your loop delay is shorter than your transmission time, data will be lost. Engineering requires this kind of calculation to prevent real system failures."
20. Exit question (written): "Name one criterion from the code review rubric and write the rule it represents in one complete sentence — as if you were writing a coding standard for a professional team." Collect.
21. Submit command-driven sketch, completed rubric, rewrite documentation, and code review report via USB flash drive.

## Safeguarding

Safeguarding Note: Learners must not type personal information (names, phone numbers, addresses, school details) into the Serial Monitor during command testing — Serial input is logged by the Arduino IDE and may be visible to others. Remind learners that the "Peer Sketch for Review" is a fictional example — no real peer's work is being evaluated. Code review feedback must remain professional and specific to the code, never personal. The code review report should be written as if addressed to a professional colleague, not a classmate.
