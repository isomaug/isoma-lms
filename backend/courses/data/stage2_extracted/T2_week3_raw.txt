Show an image (or describe): "A house has 4 teams working on it — the foundation team, the walls team, the roof team, and the finishing team. Can the roof team start before the walls are done?"
Bridge: "Building a complex programme is exactly the same. Today we have 4 sub-problems — like 4 teams. We build and TEST each one before connecting them."
Show the decomposition planning sheet. Walk through what each box means.
Introduce the brief cards. Read one aloud. Ask: "What are the 4 natural parts of this programme?"
Distribute brief cards and decomposition planning sheets.
Step 1 (4 min): Read the brief. Identify the 4 natural sub-problems and write each in a box.
Step 2 (4 min): For each sub-problem, write: which blocks are needed? What is the test condition (how will you know this sub-problem is working correctly)?
Step 3 (4 min): Write the order of building — which sub-problem MUST be built first? (Usually: triggers and basic character setup first, then effects, then coordination.)
Facilitator approves decomposition plan: "Can I see 4 clear, testable sub-problems?" Tick and proceed.
Build only Sub-problem 1 first (7 min). When complete, run ONLY that portion. Does it pass its test condition? Tick the test checklist. Only then proceed to Sub-problem 2.
Build Sub-problem 2 (7 min). Test. Tick. Proceed.
Connect Sub-problem 1 + 2 (3 min): run both together. Does the combination work as intended? Fix any integration issue now.
Build Sub-problem 3 (6 min). Test. Tick. Connect to 1+2. Run all three.
Build Sub-problem 4 (5 min). Test. Tick. Connect all four. Run full programme.
Bug at any stage? Debugger process applies: identify which sub-problem contains the bug (it is ALWAYS in the most recently added component — unless a previous test was skipped).
Facilitator checkpoint at 20 min: "How many sub-problems have been tested and ticked?"
Pairs report: how many sub-problems were fully completed? (0–4.) What blocked completion?
Class discussion: "Was it easier to debug when you built sub-problem by sub-problem? Why?"
Key insight: "A bug found when building sub-problem 3 is almost always IN sub-problem 3 — because sub-problems 1 and 2 were already tested. This is why we test each part before adding the next."
Learners annotate their decomposition sheet: circle the sub-problem that was most challenging. Write one word: why.
Save projects. Complete the test checklist.
Collect decomposition sheets for portfolios.

Big Idea
Complex problems are just lots of simple problems linked together. Break the big problem into small pieces, solve each piece, then connect them. This is DECOMPOSITION — the most powerful thinking skill in computing.

Learners write a paragraph plan BEFORE the essay — same as the sub-problem plan before the programme. Vocabulary: decompose, sub-problem, component, systematic, integrate, connect, whole, part.

ASSESSMENT
Formative (During)
Decomposition planning sheet approved: 4 sub-problems with test conditions written
Sub-problem test checklist: number of ticks recorded at end of session
Facilitator checkpoint at 20 min build: sub-problem progress noted
Debugging location correctly identified as "most recently added sub-problem"
Exit / Summative
"If you find a bug when adding Sub-problem 3, where do you look first — and why?" Learner should say: Sub-problem 3, because Sub-problems 1 and 2 were already tested and passed. Correct reasoning = full mark.
Differentiation
Support: Reduce to 3 sub-problems; facilitator pre-builds Sub-problem 1 and learner builds 2 and 3. Extension: After completing all 4 sub-problems, write a 1-page "programme specification" — a formal description of what the programme does, what each sub-problem achieves, and what inputs and outputs exist.
