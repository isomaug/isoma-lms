Pairs separate to their own tablets. BOTH pairs build simultaneously - this is the parallel work phase.
Each pair follows their Sub-system Design Strip from Lesson 17. Build task by task. Test each task before proceeding (green flag check as in Lesson 14).
CRITICAL: at the END of Sub-system A, the final block must be the SEND MESSAGE block (or page-change trigger) that was defined in the Interface Design Card.
CRITICAL: at the START of Sub-system B, the first trigger must be the RECEIVE MESSAGE (or page trigger) that was defined in the Interface Design Card.
Facilitator checkpoint at 14 minutes: each pair reports progress. Both pairs must have at least their core mechanic working before integration begins.
Complete Sub-system Test Checklist: both sub-system criteria met? Interface endpoint correctly implemented? "Can this be integrated?" - only proceed to integration if YES.
Pairs come together with both tablets. Follow the Integration Protocol Card step by step.
Step 1 (3 min): Pair A's sub-system is the primary file. Pair B transfers their characters and pages onto the same tablet (manual re-build of key elements if direct transfer is not possible on the device).
Step 2 (4 min): Connect the interface. Check: Sub-system A ends with the agreed message or page transition. Sub-system B begins with the matching receive trigger.
Step 3 (4 min): Run the full integrated programme. Complete the Integration Log: "What we expected → what actually happened → any bugs found."
Step 4 - Regression test (3 min): Run ONLY Sub-system A (disconnect Sub-system B temporarily). Does Sub-system A still work exactly as before? If not - regression bug introduced during integration. Document and fix.
Step 5 (2 min): Run full programme again. Confirm both integration success criteria are met.
Groups share integration experience: "Did the interface specification work exactly? What had to be adjusted during integration?"
Class discussion: "Was the integration harder or easier than you expected? What was the main reason for any difficulty?"
Key teaching: "Integration bugs are the most common bug in real software. The most common cause: one team built to a slightly different understanding of the specification. This is why the interface must be EXACT before building starts."

Big Idea
In professional software development, each team builds its part without waiting for the others - because the interface was defined first. When both parts are done, they are combined. If the interface was specified correctly, the integration is smooth. If not, integration reveals the mistakes.

CROSS-CURRICULAR LINKS
English
Technical communication: after building, each pair must explain their sub-system to the other pair in exactly 90 seconds before integration begins. "Our sub-system does ___. It starts when ___. It ends by sending ___. The test condition is ___." This is the verbal equivalent of a technical handover document. Vocabulary: integration, regression, handover, protocol, export, component, standalone, combined.
Maths
Block count tracking: each pair counts the total blocks in their sub-system. After integration, count the total blocks in the combined programme. Combined total should approximately equal Sub-system A blocks + Sub-system B blocks. If fewer blocks than expected - something was lost during integration. This is the integration test.

Differentiation
Support: If integration is too complex, each pair presents their sub-system independently on their own tablet. The "integration" is demonstrated by running Tablet 1 (Sub-system A) then handing Tablet 2 to the same person (Sub-system B). This approximates integration without the technical challenge. Extension: Write a post-integration report (1 page): Specification vs reality, integration steps taken, bugs found and fixed, lessons learned for the next collaborative project.
