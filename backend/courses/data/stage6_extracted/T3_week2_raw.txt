Week 2 Systems Context - Persistent State in Embedded Systems
A system with no persistent memory resets to its initial state every time it is powered off. This is acceptable for a blinking LED - it is not acceptable for a security system, a vending machine counter, or any device that must maintain state across sessions.
EEPROM (Electrically Erasable Programmable Read-Only Memory) is built into every Arduino Uno - 1,024 bytes at addresses 0–1023. It survives power-off. It can be read and written under programme control using the EEPROM.h library.
This week's session introduces the Engineering Change Log - a formal document that records every intentional change to a system. In professional engineering, no change is made without documentation. The Log answers: what was changed, why, who decided, what the expected outcome was, and whether the outcome was achieved.
EEPROM is also the introduction to the binary number system: each byte stores a value from 0 to 255, represented in 8 bits. Understanding why 1 byte = 8 bits = 256 possible values is a key computer science concept that connects directly to the P6 Mathematics curriculum (powers of 2).

When you turn a machine off and on again, most variables reset to zero. But a real product - a digital safe, a smart meter, a medical device - must remember what happened last time. EEPROM is the Arduino's long-term memory. Today you make your system remember.
English Literacy Thread
Mathematics Thread
Engineering Change Log: every professional engineering team maintains a change log - it is a contractual and safety document. Each entry must use precise technical language: not "fixed the bug" but "Changed EEPROM write address from 0 to 1 because address 0 was returning corrupted data after 3 write cycles. Expected outcome: stable read values across power cycles." Learners write 4 complete log entries during the session - this is real-time technical writing, produced alongside coding, not after. Explicit instruction: the Reason column explains the engineering decision - it is not a description of what happened, it is a justification for why a change was made.
Binary number system: 1 byte = 8 bits. Each bit can be 0 or 1. 2⁸ = 256 possible values (0–255). Convert: decimal 42 → binary 00101010. Convert binary 11001001 → decimal 201. EEPROM capacity: 1024 bytes × 8 bits = 8192 bits. Wear calculation: 100,000 writes ÷ (60 × 60 × 24) writes per day = 1.16 days if writing every second - so a system writing every second will exhaust one EEPROM address in approximately 1 day. Solution: spread writes across multiple addresses (wear levelling) - divide 100,000 by write frequency to find lifetime in seconds, then convert.

Activities & Facilitator Actions
1. HOOK The Power Cycle Problem
20 min
• Load the state machine from Week 1 on the projector. Set it to the OPEN state. Ask a learner to disconnect the USB cable and reconnect it. Observe: the system restarts in CLOSED. Ask: "Why? What was lost?" (The currentState variable was stored in RAM - it resets on power-off.)
• Ask: "Name a device in your home that must remember its setting after power-off." Collect answers: TV channel, alarm clock time, microwave clock, phone unlock pattern. "How does it remember?" Connect: persistent memory.
• Introduce EEPROM using the Reference Card. Write on board: EEPROM.write(0, 42); EEPROM.read(0); - explain address (0) and value (42). Ask: "Why can the value only be 0–255?" Connect to binary.
• Binary hook: hold up 8 fingers. Each finger is a bit. Fold all fingers down = 00000000 = 0. Raise all fingers = 11111111 = 255. "How many combinations of 8 fingers?" 2⁸ = 256.
• Distribute Binary Conversion Worksheet. Pairs complete 5 conversions (decimal to binary) before the guided activity. Facilitator cold-calls answers.
2. GUIDED ACTIVITY Integrate EEPROM with the State Machine
60 min
• Step 1 (10 min): Open the Week 1 state machine sketch. Add #include <EEPROM.h> at the top. Facilitator explains: EEPROM.h is part of the Arduino standard library - no installation needed.
• Step 2 (15 min): Add persistence to setup(): currentState = (GateState)EEPROM.read(0); - this reads the saved state on startup. Explain the cast: (GateState) converts the byte value back to the enum type.
• Step 3 (15 min): Add a save function: void saveState() { EEPROM.update(0, (byte)currentState); } - use EEPROM.update() instead of write() to avoid unnecessary wear (update only writes if the value has changed). Call saveState() at every state transition.
• Step 4 (10 min): Upload, set the state to OPEN. Open Serial Monitor - confirm "State saved: OPEN" is printed. Disconnect USB. Reconnect. Confirm "Restoring state: OPEN" prints on startup.
• Step 5 (10 min): Distribute Engineering Change Log. Facilitator models the first entry live: "Change 1: Added #include <EEPROM.h>. Reason: The EEPROM library is required to access persistent storage on the Uno. Expected outcome: EEPROM functions are available in the sketch." Learners begin their own log.
3. INDEPENDENT / PAIR WORK Wear Analysis, Binary & Documentation
50 min
• Task 1 (15 min): Complete the EEPROM Wear Calculation Sheet. Scenario: the system saves state every time a button is pressed. If buttons are pressed 10 times per day on average, how many days until address 0 wears out? Show full calculation. Then: propose a wear-levelling strategy using 10 EEPROM addresses - how does this extend the lifespan?
• Task 2 (10 min): Complete 10 remaining binary conversions on the worksheet. Final challenge: EEPROM has 1024 addresses. How many total bytes of storage? How many bits? Express as a power of 2.
• Task 3 (20 min): Complete the Engineering Change Log - minimum 4 entries covering every deliberate change made in Phases 1 and 2. Each entry must have all 5 columns completed. The Outcome column is completed AFTER testing the change.
• Task 4 (Extension, 5 min): Save TWO values to EEPROM: the state (address 0) AND a counter (address 1) that increments each time a state transition occurs and persists across power cycles. Print both on startup: "State: OPEN | Total transitions: 7."
• Rotate Driver/Navigator between Tasks 1 and 3.
4. SHOWCASE & DEBRIEF
30 min
• Live demonstration of persistence: facilitator selects one pair, puts their system in LOCKED state, disconnects USB in front of the class, reconnects - system must restore to LOCKED. Success is celebrated; failure is diagnosed together ("Which line is missing? Where should saveState() be called?").
• Engineering Change Log share: one pair reads their best entry aloud. Class evaluates: Is the Reason a justification or a description? Is the Expected Outcome specific and testable? Facilitator models the difference: "Reason: 'I changed it' is a description. Reason: 'address 0 was returning 255 on fresh Arduino, indicating uninitialised memory - I added a check to default to CLOSED when the read value is not a valid state' is a justification."
• Wear analysis: two pairs share their calculations. Which pair got the same answer? If different, trace through the calculation together on the board.
• Binary close: write 8-bit binary 10110011 on the board. Learners calculate the decimal value (179). "How many EEPROM addresses could we use to store this one number?" (Just 1 - it fits in a byte.) "What about a number above 255?" (Need 2 bytes - introduces multi-byte storage preview.)
• Collect Binary Worksheet, EEPROM Wear Calculation Sheet, and Engineering Change Log as this week's artifact.

Safeguarding Note
EEPROM has a finite lifespan (approximately 100,000 write cycles per address). Learners must use EEPROM.update() not EEPROM.write() to avoid unnecessary wear during the session - facilitator demonstrates this explicitly and explains why. Engineering Change Log: all entries are about the system, not about other learners. If a pair makes a mistake, it is logged as a technical event ("incorrect address used; corrected to address 1") - not attributed to a person. This models professional engineering culture: systems are improved, people are not blamed.
