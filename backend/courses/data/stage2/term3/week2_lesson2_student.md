# Week 2 - Lesson 2

## Session length
**About half of this week's plan** (finish what you started in Lesson 1)

## Finish the week
- Build a complete sub-system from the Lesson 17 Sub-system Design Strip, achieving all 2 sub-system-specific success criteria
- Test the sub-system in isolation before attempting integration
- Integrate Sub-system A and Sub-system B onto a single tablet, connecting them via the defined interface
- Identify and document any integration error (an error that only appears when both parts are combined) and apply the debugging process to fix it

## Continue

### DELIVER - Integration (16 min)
1. Complete Sub-system Test Checklist: both sub-system criteria met? Interface endpoint correctly implemented? "Can this be integrated?" - only proceed to integration if YES.
2. You come together with both tablets. Follow the Integration Protocol Card step by step.
3. Step 1 (3 min): Pair A's sub-system is the primary file. Pair B transfers their characters and pages onto the same tablet (manual re-build of key elements if direct transfer is not possible on the device).
4. Step 2 (4 min): Connect the interface. Check: Sub-system A ends with the agreed message or page transition. Sub-system B begins with the matching receive trigger.
5. Step 3 (4 min): Run the full integrated programme. Complete the Integration Log: "What we expected -> what actually happened -> any bugs found."

### DISCOVER - Integration Debrief (6 min)
6. Step 4 - Regression test (3 min): Run ONLY Sub-system A (disconnect Sub-system B temporarily). Does Sub-system A still work exactly as before? If not - regression bug introduced during integration. Document and fix.
7. Step 5 (2 min): Run full programme again. Confirm both integration success criteria are met.
8. Groups share integration experience: "Did the interface specification work exactly? What had to be adjusted during integration?"
9. Think about: "Was the integration harder or easier than you expected? What was the main reason for any difficulty?"
10. Key teaching: "Integration bugs are the most common bug in real software. The most common cause: one team built to a slightly different understanding of the specification. This is why the interface must be EXACT before building starts."

### WRAP-UP (4 min)
11. Groups update their Interface Design Cards with any corrections made during integration.
12. Save integrated project as "INTEGRATED PROJECT - [Group Names]."
13. Complete Integration Log final row: "Integration status: Fully connected / Partially connected / Not yet connected."
14. Preview: "Next lesson - we polish the integrated project and build the title screen and final sequence together as a group of 4."

## Check your understanding
- Formative (During)
- Sub-system Test Checklist: both sub-system criteria met before integration
- Integration Log: completed with expected vs actual outcomes documented
- Regression test passed: Sub-system A still works after integration
- Both integration success criteria met (from Collaborative Project Brief)
- Exit / Summative
- "What is an integration bug? Can you describe one specific integration issue you encountered or heard about today?" Full marks: precise description linking the bug to the interface specification mismatch.
- Differentiation
- Support: If integration is too complex, each pair presents their sub-system independently on your own tablet. The "integration" is demonstrated by running Tablet 1 (Sub-system A) then handing Tablet 2 to the same person (Sub-system B). This approximates integration without the technical challenge. Extension: Write a post-integration report (1 page): Specification vs reality, integration steps taken, bugs found and fixed, lessons learned for the next collaborative project.

## Stay safe
Safeguarding Note: During physical device sharing and transfer, ensure you handle devices carefully. Establish a clear handover procedure: one learner at a time holds the device. No device should be passed across the table unsupported.
