# Week 6 - Lesson 1

## Session length
**About half of this week's plan** (you will finish in Lesson 2)

## Today you will learn
- Use the Lesson 13 specification document as a build guide, implementing each sub-problem in order
- Test each sub-problem against its test condition before connecting it to the next
- Implement at least one page transition as a state change (e.g. PLAYING -> WIN SCREEN)
- Document any deviation from the specification during the build and justify each change made

## Big idea
The specification document is the architect's blueprint. The programmer's job is to build exactly what is on the blueprint — no more, no less. A programme that matches its specification is a success, even if it is simple.

## What you need
- 4 tablets with Stack KIDI — clean new projects
- Game Specification Documents from Lesson 13 (you returns these)
- Sub-problem test checklist from Lesson 11 (reuse format, or new A5 sheet)

## Links to English and Maths
- **English:** Following instructions precisely vs. adapting them: "A builder follows plans exactly — unless something is impossible, in which case they change the plan and document it." You must write in the Deviation Log if they change anything from the specification. Vocabulary: implement, specification, deviate, justify, document, adapt, evidence, precision.
- **Maths:** Progress tracking: at the 20-minute checkpoint, you count: sub-problems complete / in progress / not started. Calculate completion percentage: (complete ÷ 4) × 100 = ___%. At end of session: same calculation. Compare start and end percentages. Calculate rate of progress: "We completed ___ sub-problems in 40 minutes, so each sub-problem took approximately ___ minutes on average."

## Let's begin

### HOOK — The Blueprint Check (7 min)
1. Deviation log (A5 for you): 3 rows — Sub-problem changed / Reason for change / How the specification was updated. This teaches that specifications evolve — good engineers document changes.
2. Checkpoint flag cards (A6, 4 for you): green flag card held up when a sub-problem passes its test condition — you can see progress from anywhere in the room
3. Block speed reference (A5): common Stack KIDI blocks listed with their typical use in a game context — useful reference during a focused build sprint
4. You hands back Lesson 13 specification documents. You re-read your own specification silently for 2 minutes.
5. "Does this spec still make sense to you? Is anything unclear now that you are about to build it?" You flag any confusion.
6. For any flagged issue: you helps clarify or simplify the problematic section (maximum 3 minutes for you).

### DELIVER — Build Sprint (44 min)
7. Get ready to use checkpoint flag cards. Explain: "When your sub-problem passes its test condition — hold up a green flag. I will come and confirm before you proceed to the next."
8. BUILD BEGINS. You open Stack KIDI. New project. Build strictly in sub-problem order from the specification.
9. SUB-PROBLEM 1 (10 min): Typically — set up the TITLE SCREEN page: background, character, "tap to start" trigger that navigates to Page 2 (PLAYING state). When complete and tested: hold up green flag.
10. SUB-PROBLEM 2 (10 min): Typically — build the PLAYING state: the core game mechanic (tap trigger, score variable, character feedback loop). When complete and tested: hold up green flag.
11. CHECKPOINT at 20 minutes: Write down each pair's progress (green flags received). Any pair with 0 flags — receives a targeted 3-minute support session.
