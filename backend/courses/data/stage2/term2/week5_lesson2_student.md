# Week 5 - Lesson 2

## Session length
**About half of this week's plan** (finish what you started in Lesson 1)

## Finish the week
- Define a game "state" and identify at least 3 states in a given example game (Start, Playing, Won)
- Draw a state transition diagram showing all states and the triggers that move the game between them
- Write a complete game specification document including: title, character(s), 3 states, 3 transitions, success criteria (4 items), and a decomposition of 4 sub-problems
- Peer-review a partner pair's specification for completeness and testability

## Continue

### DELIVER — Game Specification Document (28 min)
1. You reviews all diagrams: "Is there a clear path from TITLE SCREEN to WIN? Can the player replay? Is every transition triggered by something specific?"
2. Open Game Specification Documents. Transfer the state diagram into Section 3 (States) and Section 4 (Transitions).
3. Section 1 — Title and Concept (4 min): Write the game title and a 2-sentence concept description: "In this game, the player ___. The goal is to ___."
4. Section 2 — Characters (3 min): Name and describe both characters (if applicable). Write one sentence about each character's role in the game.
5. Section 5 — Success Criteria (8 min): Write 4 testable success criteria. Each must be specific enough to verify by running the game: e.g. "Tapping the hero character 5 times triggers the WIN state" — not "the game is fun." Check each criterion: "How would I test this?"

### DISCOVER — Specification Peer Review (8 min)
6. Section 6 — Decomposition (10 min): Break the full game into 4 sub-problems. For each: name it, list the blocks needed, write the test condition. Base this on experience from Lesson 11.
7. You approves completed specification: "Could another programmer build this game from your document without asking you any questions?" Sign off with initials and date.
8. You swap specification documents with the adjacent pair. Complete the self-check card (5 checkboxes).
9. Return documents. Read the peer review. Address any unticked box: rewrite that section to make it clearer.
10. Class: one pair presents their state diagram (not the full spec) to yourself in 60 seconds. Class checks: "Can I follow the game flow from this diagram?"

### WRAP-UP (4 min)
11. Reflection: "Why is designing completely before coding better than just starting to build?" You write one reason each.
12. File specification documents safely — they will be used as the BUILD brief next lesson.
13. Preview: "Next lesson — we start coding. The specification document is your blueprint. Every sub-problem will be built and tested before the next one begins."
14. Collect self-check cards. You reviews all specifications overnight — flag any that need a simplification before next lesson.

## Check your understanding
- Formative (During)
- State transition diagram: 3+ states, 3+ transitions with named triggers
- Game specification: all 6 sections completed (you sign-off)
- 4 success criteria testable by running the programme (you check each)
- Peer review: 5/5 checkboxes ticked by peer, or revisions made to reach 5/5
- Exit / Summative
- You holds up one success criterion from each pair's document. "How would I test this? What would I see when I run the game?" Learner must describe a concrete observable outcome. Vague criteria are revised on the spot.
- Differentiation
- Support: Reduce to 2 states and 2 transitions; you assists with decomposition section. Extension: Add a LOSE state with a time-limit trigger. Design the transition back to PLAYING from LOSE (retry mechanic). Write a 2-sentence explanation of why the LOSE state makes the game more challenging.
